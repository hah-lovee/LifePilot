# vpn-proxy — VPN прямо на VM

Поднимает Xray с вашей VLESS-подпиской и отдаёт локальный HTTP-прокси, через
который бот и backend ходят в Telegram.

## Зачем

Telegram с VM не работает: TCP-соединение устанавливается мгновенно, а
следующий реальный запрос висит до таймаута — похоже на DPI, режущий сессию
после TLS-handshake. Замеряно многократно, из двух голосовых доходило одно.

Первым решением был прокси на ПК (`tools/telegram-proxy.py`), но он работает
только пока ПК включён и на нём поднят VPN. Здесь VPN живёт на самой VM:
зависимости от ПК нет вовсе.

## Как устроено

```
voice-bot ─┐
           ├─► vpn-proxy (Xray) ──REALITY──► VPN ──► api.telegram.org
backend   ─┘        :8889 http
                    :1080 socks
```

Порты наружу не публикуются — прокси доступен только внутри docker-сети. Это и
удерживает его от превращения в открытый релей.

За балансировщиком несколько серверов сразу, Xray сам проверяет их живость
(`observatory`, проба раз в минуту) и держит трафик на отвечающих. В подписке
их несколько десятков, и отдельные регулярно отваливаются.

## Настройка

Бинарник Xray не лежит в репозитории (36 МБ) — его нужно скачать в контекст
сборки. И конфиг генерируется из подписки:

```bash
./vpn-proxy/fetch-xray.sh

SUBSCRIPTION_URL='https://...' python vpn-proxy/generate-config.py \
    --out infra/xray-config.json --servers 8
```

`infra/xray-config.json` содержит ключи всех выбранных серверов — он в
`.gitignore`, и так и должно остаться. Ссылка на подписку тоже секрет:
передавайте её через переменную окружения, а не аргументом, иначе она осядет в
истории команд.

При смене подписки достаточно перегенерировать конфиг и перезапустить сервис.

## Проверка

```bash
docker compose logs vpn-proxy | tail -20
docker compose exec voice-bot python -c "
import urllib.request
o = urllib.request.build_opener(urllib.request.ProxyHandler({'https': 'http://vpn-proxy:8889'}))
print(o.open('https://api.telegram.org/bot123:fake/getMe', timeout=30).read())"
```

Ожидаемый ответ — `401 Unauthorized` от Telegram: токен фальшивый, но ответ
пришёл, значит туннель работает насквозь.

В логе Xray строки вида `the outbound vpnN is dead` про отдельные серверы —
норма, балансировщик их обходит. Плохо, если мёртвыми объявлены все.

## Если не заработает

Проверьте, что VM вообще видит серверы подписки:

```bash
docker compose exec vpn-proxy sh -c 'getent hosts de1.gofizzin.com && echo DNS-OK'
```

Отдельно стоит знать: на машине, где уже работает Happ (или другой клиент с
TUN), этот контейнер работать не будет — его трафик пойдёт в тот же VPN вторым
слоем, и REALITY-хендшейк оборвётся с EOF. На VM такого клиента нет, но на
dev-ПК это делает локальную проверку невозможной.
